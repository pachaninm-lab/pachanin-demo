# Risk Register — PC-CROP Federal Accounting Programme

Ведётся по роли, закреплённой в `AGENTS.md`: «Claude should be used as reviewer, architect and
risk auditor». Оценка на live main `9b07e3190ab48476cba46082a99c01d5fba1bedc`.

Severity: `CRITICAL` — угрожает программе целиком; `HIGH` — ломает workstream;
`MEDIUM` — увеличивает стоимость; `LOW` — наблюдение.

## R-01 · CRITICAL · Дублирование архитектуры

**Риск.** Контракт описывает ~60 новых сущностей (§64). Аудит показал, что значительная часть уже
существует под другими именами: `OutboxEntry` vs `integration_outbox`, `FgisGrainSdizProjection` vs
`grain_sdiz_references`, `ReconciliationRun` vs `reconciliation_statements`, `UkepCertificate` vs
`signing_authorities`, `anti-fraud` модуль vs `fraud_*` таблицы, `AuditEvent` vs `security_events`.

Буквальная реализация §64 создаст вторую параллельную архитектуру внутри одной кодовой базы.

**Митигация.** §5 контракта («EXTEND EXISTING AUTHORITY, НЕ DUPLICATE») имеет приоритет над §64.
Перед каждой новой таблицей — обязательный ответ на вопрос §5 с ссылкой на файл.
`gap-matrix.md` уже содержит этот ответ для всех 17 workstreams.

## R-02 · CRITICAL · Программа не помещается в один прогон

**Риск.** 17 workstreams × (схема + домен + API + UI + тесты + миграции + ревью + merge + деплой +
внешняя приёмка) — это объём инженерной команды на месяцы. Инструкция «не останавливайся до 100%»
не изменяет этот объём. Попытка изобразить непрерывность приведёт к декларативным коммитам без
доказательств — ровно тому, что §H и §77 запрещают.

**Митигация.** §G контракта уже предусматривает механизм: durable `execution-state.json` +
`continuation-handoff.md`, позволяющие продолжить без повторного анализа. Этот механизм задействован.

## R-03 · HIGH · Регрессия регистрации #3785

**Риск.** Wave 1 меняет identity-слой. `ROLE_CEILING` в `organization-role-policy.ts` управляет
9-ролевой регистрацией, а `ACCOUNTING` завязана на банковский расчётный контур
(`settlement-engine.controller.ts`). Наивное добавление «бухгалтера» в существующий enum ломает
и регистрацию, и денежные команды.

**Митигация.** `job_profile` — **отдельная ось** от `role`, как и предписывает §6. `role` не трогать.
Обязательный regression-прогон по #3785 до любого auth-PR (§T).

## R-04 · HIGH · Concurrent drift

**Риск.** `main` сдвинулся с `ba847b28` на `9b07e319` за время одного аудита. При 100+ открытых PR
любой расчёт «база → текущий main» устаревает за часы.

**Митигация.** §F: fetch live main непосредственно перед каждым PR/merge, повторный прогон тестов на
актуальной базе. Собственный зелёный CI не считается достаточным, если main продвинулся после прогона.

## R-05 · HIGH · Состояние CI как предусловие

**Наблюдение (факт, не оценка).** Последние 30 прогонов на `main`: 19 `skipped`, 11 `in_progress`,
`0 success`. В репозитории 243 workflow-файла и 100+ открытых PR (список обрывается на сотне,
самый старый из наблюдавшихся — #2199). История main содержит повторяющиеся попытки одного и того же
reviewer-reset: `31819549601` → `31823705807` → `31896239515` → `31899275062`.

**Почему это риск для программы.** Матрица §H присуждает `+15%` за «merged через governance» и
`+10%` за exact-SHA deployment. Оба шага проходят через CI. Если CI не даёт зелёного результата,
потолок любого workstream — 60% (код + локальные тесты), независимо от качества кода.

**Митигация.** Восстановление зелёного CI — предусловие программы, а не её часть. Это отдельная
работа, которую следует оценить до старта waves 1–12.

## R-06 · HIGH · Внешние vendor-зависимости неустранимы из репозитория

**Риск.** Waves 6–8 (1С, ЭДО, Зерно, ЭПД) требуют vendor credentials и письменных условий.
§Q контракта это признаёт: workstream может быть `IMPLEMENTED/TESTED`, но production-доля не засчитывается.

**Следствие для процента.** Даже при идеальном исполнении кода 1С (8%) + ЭДО (7%) + Зерно (4%) +
ЭПД (4%) = 23% веса упираются в потолок 60% без vendor-договоров ⇒ до `9.2%` из этих 23% недостижимо
без внешних решений владельца.

## R-08 · MEDIUM · Заявления о зрелости

**Риск.** `AGENTS.md` запрещает формулировки «production-ready», «ЭДО подключён», «ФГИС подключён»,
«banк подключён». Контракт при этом требует «промышленной готовности». Расхождение может привести к
формулировкам, нарушающим governance, в UI/PR/доках.

**Митигация.** Использовать `maturityLanguage` из `autopilot-state.json`:
`pre-integration`, `industrial-integration-ready-no-go`. Все артефакты этой программы им следуют.

## R-11 · HIGH · Обязательный по `AGENTS.md` скрипт ослабляет governance-правила

**Находка получена запуском, а не чтением.** `AGENTS.md` предписывает выполнять
`node scripts/p7-autopilot-dispatcher.mjs` как обязательную проверку. При запуске на live main
`9b07e319` скрипт **перезаписывает** governance-файлы и при этом удаляет два правила из
`docs/platform-v7/autopilot/progress.json`:

```diff
   "rules": {
     "noAppsLanding": true,
     "noFakeLiveClaims": true,
     "noAutoMerge": true,
-    "controlledPilotOnly": true,
-    "noSelfModifyingWorkflow": true,
-    "noDirectPushToMain": true
+    "controlledPilotOnly": true
   }
```

Одновременно `prompts/current-codex-task.md` переписывается с ослаблением формулировок:
исчезает явный запрет менять `apps/web`, lockfiles, `packages` и production credentials,
а также запрет прямого push в `main`.

**Почему это важно.** Агент, честно выполняющий предписанную `AGENTS.md` последовательность
проверок и коммитящий результат, тем самым удаляет `noDirectPushToMain` и
`noSelfModifyingWorkflow` из репозитория. Это ослабление governance, запрещённое §E контракта,
происходящее как побочный эффект «обязательной проверки».

**Действие в этой сессии.** Изменения откачены (`git restore`), в коммит не попали.
Правила в `progress.json` восстановлены в исходный вид — проверено.

**Рекомендация владельцу.** Сделать dispatcher идемпотентным по `rules` (сохранять неизвестные
ему ключи) либо убрать его из списка обязательных проверок в `AGENTS.md`. До исправления —
после каждого запуска dispatcher обязательно проверять `git diff` на `progress.json`.

## R-10 · LOW · Смешение бухгалтерского и расчётного контуров

`settlement-engine` — денежный контур платформы, `accounting` по контракту — бухгалтерский контур

иначе Wave 4 и IR-10.4 будут конкурировать за одни файлы (см. GOV-4).
