# Gekta registration document evidence

The registration form shows Gekta documents. Its receipt must describe those exact documents rather than the platform's separate terms/privacy pair. The existing two unchecked checkboxes remain separate choices; the current public version and document copy are unchanged.

The server renders the existing documents with the actual current merchant disclosure, hashes the full rendered document together with its version, Russian document language and current merchant-profile digest, and binds both documents, their purposes, profile identity/effective date and interface language into a short-lived signed form commitment. EN/ZH interfaces still link to Russian documents; the receipt records that distinction. An unconfigured merchant is recorded as unconfigured, never as verified legal identity.

The BFF verifies that commitment against its actual current rendered documents before registration or email side effects. A changed profile, document, interface language or expired form requires a page reload and two new unchecked choices. It forwards its own verified public document snapshot over the existing internal registration-delivery boundary. The API requires that boundary and verifies the same signed snapshot before password hashing or a database transaction. A public direct API request cannot create an account without this document evidence.

The existing hash-chained auth audit stores the full public rendered documents, document/profile digests, interface/document languages, purposes, form-issued and server-accepted timestamps and the two existing accepted booleans. There is no additional consent database, secret in a receipt, or snapshot signature in an audit/log. Platform consent policy remains separate. Links carrying a version/hash/profile commitment display that exact current document or reject a stale link instead of silently displaying changed content.

This is evidence of the explicit choices and the form presentation, not proof that a person read the documents. The commitment does not authenticate a user and can be reused while current; existing account identity, password, email verification, CSRF, rate limits and mandatory MFA remain the account authority. Legal review, operator verification, registered-consent withdrawal, retention/backup policy and the anonymous notice's full document binding remain separate acceptance items. This source preparation alone does not prove runtime deployment or complete privacy acceptance.
