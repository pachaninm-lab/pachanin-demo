# 0 Статус и границы документа

## 0 1 Remaining only

Существующий регистрационный и доменный фундамент не реализуется заново. Классификация KEEP требует текущего evidence; перечисление ниже является границей защиты, а не заявлением о свежей production-проверке. Подтверждённые функции остаются в regression acceptance, а в кодирование попадают только выявленные пробелы и дефекты.

Защищённый базис:

- Registration и Identity;
- Role Eligibility и MFA;
- server-derived role, tenant и organization context;
- RLS и tenant isolation;
- PostgreSQL authority;
- audit и transactional outbox;
- существующие Canonical Deal, Settlement, Service Provider, Integration и Marketplace foundations;
- существующие release, IP Clean Room и security boundaries.

Активный remaining scope начинается с фактической инвентаризации текущего `origin/main`, открытых PR, веток, production release и live-состояния. Исторический PASS не переносится на новый SHA.

Начальное бухгалтерское значение этого ТЗ:

`OVERALL_PRODUCTION_PROGRESS = 0/100 = 0%`

Это не оценка готовности всего проекта. Это означает, что ни один remaining-блок ещё не подтверждён по новому Definition of Done. После R0 Codex вправе зачесть уже существующий блок только при доказанном совпадении требований, exact-current-main release и свежем live acceptance.

## 0 2 Registration boundary

`[REQ-BAS-001]` Не перестраивать регистрацию и не расширять её post-registration функциями.

`[REQ-BAS-002]` Для каждого выпуска обязательно: `REGISTRATION_CODE_CHANGED=0`, если изменение не требуется доказанным production-дефектом.

`[REQ-BAS-003]` Обязательно: `REGISTRATION_BEHAVIOR_CHANGED=0` и `ROLE_ELIGIBILITY_REGRESSION=0`.

`[REQ-BAS-004]` Если исправление общего компонента технически затрагивает регистрацию, Codex обязан доказать behavioural parity отдельной матрицей и тестами.

## 0 3 Нулевые новые обязательные расходы

`[REQ-CST-001]` Новые обязательные платные API, SaaS, базы данных, LLM API, сервисы мониторинга и внешние лицензии запрещены, если результат достижим существующим стеком и инфраструктурой.

`[REQ-CST-002]` Любое предложение нового обязательного расхода требует измеренного доказательства невозможности бесплатного или уже оплаченного варианта, стоимости, эффекта, рисков и отдельного решения владельца.

`[REQ-CST-003]` Технологическая экономия не может ослаблять безопасность, юридическую корректность, целостность денег или данных.

# 1 Исполнительный контракт Codex

## 1 1 Режим работы

`[REQ-EXE-001]` Перед первым изменением Codex обязан прочитать применимые `AGENTS.md`, governance, release, security и repository-specific инструкции. Более высокий системный или security policy всегда имеет приоритет.

`[REQ-EXE-002]` Codex проверяет решение с позиций архитектуры, backend, frontend, UX, QA, DevOps, security, data, AI, product и compliance. Это стандарт полноты работы, не заявление о наличии людей или всезнании. Делегирование допускается только если разрешено инструкциями среды и текущей задачей; независимые проверки можно выполнять параллельно без параллельного запуска других delivery slices.

`[REQ-EXE-003]` Нельзя использовать пользователя как диспетчера обычной разработки: не спрашивать разрешение на безопасные действия, прямо входящие в это ТЗ и доступные в текущих permissions.

`[REQ-EXE-004]` В пределах активной рабочей сессии Codex не останавливается ради промежуточного отчёта, пока остаётся безопасная внутренняя работа по текущей атомарной задаче.

`[REQ-EXE-005]` Плановая остановка ради отчёта допустима после `PRODUCTION_PASS` текущей атомарной задачи. Обязательная остановка также требуется при нехватке authority/approval, угрозе данным/деньгам, прямой команде остановиться или техническом прекращении сессии. При внешнем блокере действовать по разделам 7.1 и 10; запрещено скрывать причину или обещать бесконечную фоновую работу.

`[REQ-EXE-006]` После полного выпуска одной атомарной задачи Codex даёт короткий статус с процентом и сразу продолжает следующую разрешённую задачу зафиксированной очереди. Одна полноценная атомарная задача включает backend/data/UI/tests/release, необходимые для её результата; commit или документационный подэтап не считается самостоятельным production-результатом. Dependency promotion и внешние блокеры обрабатываются по 7.1 без ложного закрытия R-блока.

`[REQ-EXE-007]` Скорость достигается ранним исследованием, малыми PR, повторным использованием архитектуры, параллельными безопасными проверками, контрактными тестами и устранением причин дефектов. Ослабление gate, пропуск теста и перенос ошибки на потом скоростью не считаются.

`[REQ-EXE-008]` Codex обязан предугадывать соседние сценарии и совместимость до кодирования: схема данных, состояния, permissions, мобильный UX, отказ внешнего провайдера, rollback и migration должны проектироваться вместе с основным happy path.

`[REQ-EXE-009]` До изменения архитектуры выполняется bounded repo-gap audit с классификацией `KEEP`, `EXTEND_EXISTING`, `NEW_REQUIRED`, `REMOVE_OR_SUPERSEDE`, `EXTERNAL_BLOCKER`, `NOT_REQUIRED`.

`[REQ-EXE-010]` Запрещено создавать `DealV2`, `SettlementV2`, `IntegrationV2`, `ServiceProviderV2` или параллельное ядро только потому, что существующий объект требует расширения.

## 1 2 Иерархия решений

При конфликте действуют уровни сверху вниз:

1.  системные правила, безопасность, permissions и закон;
2.  применимые обязательные инструкции репозитория и среды, включая approvals;
3.  свежая явная команда владельца в этих границах;
4.  настоящий внешний контракт или официальный первичный источник;
5.  это ТЗ и его бизнес-инварианты, включая нормализованный канон MASTER;
6.  фактическое состояние `origin/main`, production и данных;
7.  остальные architecture decision records;
8.  implementation preference Codex;
9.  старые сообщения, старые PASS, макеты и устаревшая документация.

`[REQ-EXE-011]` Не использовать прежние частные советы пользователя о кодировании как замену инженерному анализу. Codex самостоятельно выбирает совместимую реализацию по этому ТЗ, текущему коду, проверенным источникам и применимым инструкциям. Явные действующие ограничения пользователя и инструкции среды сохраняют силу; конфликт фиксируется, а не молча игнорируется.

`[REQ-EXE-012]` Codex может самостоятельно менять реализацию, декомпозицию и усиливать acceptance, но не может удалять бизнес-требование, ослаблять gate, уменьшать scope или объявлять внешний успех без evidence.

`[REQ-EXE-013]` Любое существенное изменение scope фиксируется в `scope-delta/decision-log`: до, после, причина, риск, evidence, влияние на прогресс.

## 1 3 Исследование и интернет

`[REQ-SRC-001]` При любом материальном вопросе о законе, ФГИС, API, криптографии, банке, ЭДО, ЭПД, стандарте, библиотеке или уязвимости Codex обязан свериться со свежим официальным первичным источником.

`[REQ-SRC-002]` Иерархия источников: закон и официальный реестр → официальный регламент/API/schema → официальный оператор/разработчик → проверенная техническая документация → вторичный источник только как указатель.

`[REQ-SRC-003]` Search snippet, форум, маркетинговая статья и память модели не являются контрактом.

`[REQ-SRC-004]` Для каждого внешнего контракта хранить `source URL`, владельца, дату проверки, версию, digest локального snapshot, применимые capabilities и maturity.

`[REQ-SRC-005]` Если официальный контракт недоступен, нельзя угадывать payload, статус или юридическую семантику. Создаётся provider-neutral port, fixture/contract harness и `EXTERNAL_BLOCKER_RECORD`; capability остаётся `CONTRACT_PENDING`.

`[REQ-SRC-006]` Если интернет временно недоступен, Codex продолжает внутреннюю работу, но не повышает maturity до `PUBLIC_SPEC_VERIFIED` и не объявляет внешний контур live-ready.

## 1 4 Полномочия и безопасные ограничения

`[REQ-AUT-001]` Разрешены commits, ветки, PR, исправление findings, merge после всех обязательных PASS, штатный exact-SHA release и live read-only acceptance, если это допускают доступные permissions и repository policy.

`[REQ-AUT-002]` Запрещено обходить MFA, подпись, CAPTCHA, approval, protected branch, security control, чужие credentials, юридическое согласие или ограничение внешней системы.

`[REQ-AUT-003]` Запрещены реальные платежи, юридически значимые подписи, государственные mutation, отправка документов и сообщения внешним людям только ради теста.

`[REQ-AUT-004]` Без отдельной команды владельца не отправлять письма, сообщения, заявки, invitations и иные внешние коммуникации.

`[REQ-AUT-005]` Внешний blocker изолируется; вся независимая внутренняя работа продолжается.

# 2 Источники истины и начальный discovery

## 2 1 Фактическая точка старта

Перед каждым R-блоком Codex обязан:

1.  выполнить `git fetch origin main`;
2.  определить exact `origin/main`, текущую ветку, worktree и незакоммиченные изменения;
3.  сохранить пользовательские и unrelated изменения;
4.  найти связанные open PR, ветки, commits, migrations, CI runs и release evidence;
5.  определить production SHA и сравнить его с remote main;
6.  проверить реальные route, role, capability, schema, API, UI и live-state;
7.  обновить gap map и traceability до изменения кода.

`[REQ-DIS-001]` SHA, номера PR и проценты из этого документа не считать актуальными без повторной проверки.

`[REQ-DIS-002]` Git history, закрытые PR и CI evidence изучаются как материал, но не заменяют тест на текущем exact head.

`[REQ-DIS-003]` Production является источником истины только о фактически выпущенном поведении; ошибочное production-поведение не отменяет более высокий бизнес-инвариант.

# 3 Архитектурные инварианты

## 3 1 Каноническая архитектура

`Human UX / Role Workspace → Capabilities / Policies / Config → Canonical Domain Core → Inventory / Market / Deal / Services → Evidence / Documents / Finance → Integration Gateway → Provider Adapters`

`[REQ-ARC-001]` Один Canonical Deal и один канонический lifecycle сделки для всех ролей.

`[REQ-ARC-002]` Роль является линзой над общими объектами, а не отдельной системой с собственной истиной.

`[REQ-ARC-003]` PostgreSQL является authority для внутренних бизнес-состояний; browser state, cache, event stream и AI не могут самостоятельно финализировать состояние.

`[REQ-ARC-004]` Role, tenant, organization, permissions и high-risk capability выводятся сервером из аутентифицированного контекста.

`[REQ-ARC-005]` Деньги хранятся в minor units/decimal с валютой и правилами округления; `float` запрещён.

`[REQ-ARC-006]` Каждое критичное изменение атомарно связывает domain mutation, audit и outbox.

`[REQ-ARC-007]` Все повторяемые команды имеют idempotency key, request hash, actor, tenant, expiry и детерминированный повторный ответ.

`[REQ-ARC-008]` Optimistic concurrency или эквивалентная защита обязательна для партии, предложения, сделки, документа, обязательства, payment instruction и regulatory submission.

`[REQ-ARC-009]` Неизвестный исход внешней mutation хранится как `UNKNOWN/PENDING_RECONCILIATION`, а не как success или automatic retry.

`[REQ-ARC-010]` Данные разных tenant не смешиваются в запросах, кеше, логах, аналитике, поиске, экспорте и AI context.
